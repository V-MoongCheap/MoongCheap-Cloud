## 5. NAT Instance 기종 선정 및 비용 계산 (서울 리전 On-Demand 기준)

### 5.1 기종 선정

NAT 역할만 수행하면 되므로 상시 고성능이 필요 없고, 저렴하면서 충분한 네트워크 대역폭(최대 5Gbps)과 최소한의 메모리 여유가 있는 인스턴스면 충분합니다.

| 후보 vCPU / 메모리 서울 리전 On-Demand 평가  |                 |                     |                                                                                                         |
| --------------------------------- | --------------- | ------------------- | ------------------------------------------------------------------------------------------------------- |
| t4g.nano / t3.nano                | 2 vCPU / 0.5GiB | 약 $0.0052\~0.0065/h | 가장 저렴하지만 0.5GiB는 다수 팀원이 동시에 이미지 pull·apt·terraform provider 다운로드 등을 할 때 커넥션 트래킹(conntrack) 여유가 부족할 수 있음 |
| **t3a.micro (선정)**                | 2 vCPU / 1GiB   | **$0.0117/h (확인됨)** | 나노 대비 메모리 2배로 다수 동시 연결에 여유, AMD 기반이라 t3 대비 저렴, 버스터블 크레딧으로 순간 트래픽도 대응 가능                                 |
| t3.micro                          | 2 vCPU / 1GiB   | 약 $0.013/h (추정)     | t3a.micro와 스펙 동일하나 소폭 더 비쌈                                                                              |
| t4g.micro                         | 2 vCPU / 1GiB   | 약 $0.0104/h (추정)    | t3a.micro와 유사하게 저렴하나, ARM이라 NAT Instance AMI(주로 x86 기반 배포판) 호환성을 별도 확인해야 함                              |

**→ 선정:** **`t3a.micro`** (2 vCPU / 1GiB, 서울 리전 On-Demand **$0.0117/시간**)

- 이유: 메모리 여유(1GiB)로 팀 전체 트래픽을 안정적으로 처리, x86 기반이라 표준 NAT AMI/Amazon Linux 호환성 문제 없음, nano 대비 시간당 차액은 한 달에 약 $4 수준이라 안정성 대비 부담 없음
- 운영 시 필요 조치: **소스/대상 확인(Source/Dest Check) 비활성화**, **Elastic IP 연결**(연결된 상태에서는 EIP 자체 요금 없음), Private Subnet Route Table의 default route를 NAT Instance ENI로 지정, 장애 시 Terraform으로 재생성 가능하도록 스크립트화

### 6.3 System Add-on(ArgoCD·Jenkins·모니터링 스택) 배치 가능 여부 검토

인프라팀에서 운영할 ArgoCD, Jenkins, Prometheus/Grafana/Loki 등도 EKS 위 Pod로 떠야 합니다. 지금 나온 노드 구성(FE `t3.large`, BE `t3.xlarge`, AI CPU `m7i.large`, GPU `g4dn.xlarge`)에 여유 공간이 있는지 검토했습니다.

**1) 기존 노드의 여유 용량 (Request 기준 추정)**

| 노드 스펙 이미 배치된 Pod Request 대략적인 여유  |                |                                                                                      |                                                            |
| --------------------------------- | -------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| FE (`t3.large`)                   | 2 vCPU / 8GiB  | FE Pod (수치 미확정, 가볍게 잡아도 0.5vCPU/1GiB 내외로 추정)                                         | 약 1\~1.5 vCPU / 6\~7GiB (k8s 시스템 예약분 제외 전 기준)              |
| BE (`t3.xlarge`)                  | 4 vCPU / 16GiB | BE 요구사항상 최소 4 vCPU/8GiB                                                              | CPU 여유 거의 없음, 메모리만 약 8GiB 여유                               |
| AI CPU (`m7i.large`)              | 2 vCPU / 8GiB  | API(0.25/0.5Gi) + Embedding(0.5/3Gi) + Cluster Matcher(0.25/1Gi) = 1.0 vCPU / 4.5GiB | 약 1 vCPU / 3.5GiB                                          |
| GPU (`g4dn.xlarge`)               | 4 vCPU / 16GiB | LLM Pod (GPU 1개 + 2vCPU/8Gi)                                                         | 약 2 vCPU / 8GiB 여유하지만 taint로 다른 Pod 진입 자체가 차단됨 → 사실상 사용 불가 |

**2) System Add-on 예상 소요 (러프한 추정치 — 실측 필요)**

| 구성 요소 CPU (request) 메모리 (request) 비고         |                     |                 |                                                    |
| -------------------------------------------- | ------------------- | --------------- | -------------------------------------------------- |
| ArgoCD (server+repo-server+controller+redis) | 0.5\~1 vCPU         | 1\~1.5GiB       | 미니멀 구성 기준                                          |
| Jenkins Controller                           | 0.5\~1 vCPU         | 1\~2GiB         | 동적 Agent는 빌드 시마다 별도로 0.5\~1vCPU/1\~2GiB를 추가로 순간 소모 |
| Prometheus+Grafana+Loki+Alertmanager 등       | 1\~1.5 vCPU         | 2\~3GiB         | 소규모 클러스터 기준                                        |
| Karpenter, 기타 소소한 Add-on                     | 0.2\~0.3 vCPU       | 0.3\~0.5GiB     |                                                    |
| **합계 (Jenkins 빌드 순간 부하 제외)**                 | **약 2.2\~3.8 vCPU** | **약 4.3\~7GiB** |                                                    |

**3) 결론**

FE·AI CPU 노드에 남는 여유(약 2\~2.5 vCPU / 9.5\~10.5GiB)와 Add-on 예상 소요(약 2.2\~3.8 vCPU / 4.3\~7GiB)를 비교하면 CPU 기준으로는 딱 맞거나 빠듯하고, 특히 Jenkins 빌드가 도는 순간에는 여유를 넘어설 가능성이 높습니다. BE 노드는 이미 최소 요구사항만으로 CPU가 꽉 차 있어 추가로 얹을 수 없고, GPU 노드는 taint 때문에 애초에 후보가 아닙니다.

- \*"여유가 없으면 노드를 추가해야 하는가, 노드 사양을 올리면 되는가"\*\*에 대해서는 아래 세 옵션 중 팀 논의를 통해 선택이 필요합니다.

| 옵션 방식 비용 영향 (16h×23일 기준) 장단점             |                                                                                            |                                           |                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------------------- |
| **A. 전용 System Add-on 노드 추가**            | ArgoCD·Jenkins·모니터링 스택을 위한 노드를 별도로 하나 더 생성 (예: `t3.large` 또는 `m7i.large`)                  | 약 +$38\~46                                | 앱 워크로드(FE/BE/AI)와 완전히 분리되어 Jenkins 빌드 부하가 서비스에 영향을 주지 않음. 노드가 하나 늘어 관리 포인트도 늘어남 |
| **B. 기존 노드 사양 상향**                       | 예: AI CPU 노드를 `m7i.large` → `m7i.xlarge`(4vCPU/16GiB)로, 또는 FE 노드를 키움                       | 약 +$38\~46 (m7i.large→xlarge 시 시간당 차액 기준) | 노드 개수는 그대로라 관리는 단순하지만, 같은 노드 안에서 AI/FE Pod와 Add-on이 계속 자원 경합 — 격리가 안 됨          |
| **C. 우선 기존 여유 공간에 최소 구성으로 배치, 필요시에만 확장** | 지금은 자원 요청을 최소로 잡아 기존 FE/AI 노드에 얹고, 실제 리소스 사용량을 모니터링하다가 Pending/Evicted가 발생하면 그때 A 또는 B로 전환 | 추가 비용 없음 (전환 전까지)                         | 가장 비용 효율적이지만, Week2\~3처럼 바쁜 시점에 갑자기 리소스 부족 문제가 터질 위험 있음 → 모니터링을 게을리하면 안 됨       |

`인프라·HA·비용 차별화 전략 문서`에도 "System Add-on은 초기 On-Demand로 운영하고, 전용 NodePool 분리 여부는 서비스 구성·비용 산정 후 결정"이라고 되어 있어 원래 열려 있던 사안입니다. 6.2절 기준 예산 여유(약 $299)를 고려하면 A 또는 B를 선택해도 예산상 무리는 없어 보이나, 위 수치는 러프 추정치라 실측 후 조정이 필요합니다.

## 8. Redis(ElastiCache) 처리 방안

BE팀에서 "여유가 있으면 추가, 없으면 보류"로 요청한 사항이라 조건부 기준으로 정리했습니다.

| 옵션 방식 비용 장단점                        |                           |                                       |                                                                                           |
| ----------------------------------- | ------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------- |
| **A. 기본안 — 자체 호스팅 Redis (EKS Pod)** | Redis를 컨테이너로 EKS 위에 직접 배포 | 추가 비용 없음 (기존 Node 리소스 내에서 흡수)         | 관리형 대비 가용성·백업 자동화가 없음. 트래픽이 작은 프로젝트 규모에서는 충분                                              |
| **B. 예산 여유 시 — Amazon ElastiCache** | 관리형 Redis 사용              | 월 약 $34.31 (24h 기준, 실 가동시간 기준이면 더 적음) | 운영 부담 적음, 백업·장애 대응 자동화. 6.2 기준 예산 여유(약 $299)가 있어도 다른 변수(GPU 초과 사용, 트래픽 증가 등)에 대비한 버퍼가 줄어듦 |

### 권장 운영 규칙

1. 기본값은 A(자체 호스팅)로 시작 — BE팀 요청 기능(Session/Cache 등)이 자체 호스팅으로도 충분한지 먼저 확인
2. Week 2 종료 시점(9/20 전후)에 실제 비용 소진율을 확인 → Cost Explorer 기준 예산의 50% 미만 사용 중이면 B(ElastiCache)로 전환 검토
3. 전환하더라도 Redis가 실제로 어떤 기능(Session/Cache/PubSub)에 쓰이는지를 먼저 BE팀에게 확인 (13장 Action Item)

## 11. 타 팀 협업 프로세스 (접속 매뉴얼 제공 및 변경 요청)

**원칙**: 모든 AWS/KT Cloud 리소스의 생성·삭제는 **인프라팀이 Terraform으로만 수행**합니다. 타 팀은 콘솔에 직접 접근하거나 리소스를 직접 조작하지 않습니다.

### 11.1 리소스 제공 방식

인프라팀이 리소스를 프로비저닝한 뒤, 각 팀에 **접속 매뉴얼**을 제공합니다. 매뉴얼에는 다음 내용이 포함됩니다.

- 서비스별 엔드포인트/도메인
- 배포 방법 (예: ECR Push, ArgoCD Sync 트리거 방법)
- 로그/모니터링 대시보드 접근 경로 (Grafana 등)
- 환경변수/Secret 전달 방식 (K8s Secret 등)
- 문의 채널

### 11.2 변경·삭제·재시작·스펙 상향 요청 프로세스

타 팀에서 리소스 관련 이슈(스펙 부족, 재시작 필요, 설정 변경 등)가 생기면 아래 흐름을 따릅니다.

승인보류/추가 논의타 팀: 이슈 발생요청 문서 작성인프라팀 접수검토비용·영향도 확인Terraform으로 반영요청 팀과 협의요청 팀에 완료 공지

### 11.3 요청 문서 템플릿 (안)

| 항목 작성 내용  |                                  |
| --------- | -------------------------------- |
| 요청 팀      |                                  |
| 요청일       |                                  |
| 대상 리소스    | 예: BE Pod, AI GPU 노드 등           |
| 요청 유형     | 스펙 상향 / 재시작 / 설정 변경 / 삭제 / 신규 생성 |
| 사유        |                                  |
| 희망 스펙·설정값 | 예: cpu 0.5→1, mem 1Gi→2Gi        |
| 긴급도       | 낮음 / 보통 / 높음                     |
| 영향 범위(예상) | 다운타임 발생 여부 등                     |

### 11.4 처리 원칙

- 인프라팀은 요청 접수 시 \*\*비용 영향(예산 대비 증감)\*\*을 우선 확인 후 반영
- 반영은 반드시 **Terraform 코드 변경 + PR**로 처리하며, 콘솔에서 직접 반영하지 않음
- 긴급 대응(예: 서비스 다운)이 발생해 즉시 조치한 경우에도, 사후에 반드시 Terraform 코드에 반영해 실제 상태와 코드가 어긋나지 않도록 함
- 처리 결과는 요청 팀에 공지

> 요청 접수 채널(Notion 폼 / Slack / Discord 등)은 아직 미정 — 13장 Action Item 참고
